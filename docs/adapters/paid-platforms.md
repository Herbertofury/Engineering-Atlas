## Evidence and capability language

**Official docs verified** means the exact linked primary page documents the named capability. **Publicly observed** means public creator/platform UI or a platform administrator response supports the limited observation; it does not prove paid-body access or stable selectors. **Authorized login needed / unverified** means implementation must obtain a legitimate account fixture before declaring support. Absence of a reader API in this review is not proof that none exists.

Source reading depth is recorded per URL in the [central catalog](../../data/site-adapter-catalog.json). Official search extracts, unreadable documentation shells and failed URLs are discovery evidence, not page-body verification. The table's subject labels summarize what was researched; consult that source receipt before relying on an exact field, endpoint or policy clause. The focused primary-section pass and its retained failures are in the [source verification receipt](../../experiments/site-adapter-discovery/source-verification-2026-10-28.json).

Keep `localFollow`, `nativeFollow`, `newsletterSubscription`, `paidMembership`, `productOwnership`, `tierEntitlement`, `perObjectAccess`, and `downloadAllowed` separate. A local Follow only saves a creator in this app. It must never start a paid subscription, buy an item, renew membership, tip, activate a license, spend download credits or unlock pay-per-view material. Native follow writes require a user request and verified free action semantics. Never infer entitlement from a mirror such as Kemono; mirror provenance belongs in a separate adapter family and never supplies proof of the user's legitimate access.

Every source URL below is official unless explicitly described as an observed creator page. Rows do not assert that arbitrary session automation is allowed by platform terms. Respect access boundaries, bot challenges, rate limits, download controls and DRM. Use manual/open-in-site fallback where full extraction is unsupported.

## Policy gates before implementation

**LoyalFans: policy-blocked for automated collection.** Its official terms, last modified July 8, 2026, prohibit scraping/data mining and automated access, copying or monitoring. Manual monitoring/copying outside the terms also requires written consent. Subscription access or a creator-enabled download does not authorize an automated collector. Until separate platform authorization is established, accept only user-provided metadata and permitted manual account links, or social embeds the platform approves. Do not schedule profile polling or automatic metadata enrichment. [Official terms, Prohibited Uses and Linking sections](https://www.loyalfans.com/legal/terms-conditions).

**SubscribeStar: official API existence does not establish an accepted off-platform reader.** Both origin references say: “You will not use the API to provide any benefits outside the platform.” This is a specific disqualifying constraint for the proposed full-content API reader unless platform permission is established. The documented scopes and schema can support permitted research/integration within their conditions; they do not prove arbitrary patron-post extraction. Keep `subscribestar.com` and `subscribestar.adult` as separate platform, credential and policy origins; do not assume authorization granted for one applies to the other. [SubscribeStar API terms](https://www.subscribestar.com/api) · [SubscribeStar.adult API terms](https://subscribestar.adult/api).

These are researched policy findings, not runtime test results. The [authenticated-research workflow](authenticated-research.md) establishes account/entitlement evidence, while the [validation gate](validation-and-adoption.md) also requires the selected collection method to be permitted. Rejected alternative: a universal logged-in scraper would conflate account access with platform permission and produce false support claims; a capability-specific API/feed/manual route is the conditional candidate.

### Concrete methods and field boundaries

**Buy Me a Coffee.** The current September 1, 2026 post guide documents title/description, categories, albums and public/supporter/member visibility; video is embedded from another platform. The [audio guide](https://help.buymeacoffee.com/en/articles/6264548-how-to-publish-an-audio-post) documents uploaded/recorded audio and membership-level restriction. A reader should preserve body order, album order, external embed origin and thumbnail roles. These are mapping proposals, not verified selectors or API keys. The follow guide documents email/login handoff, `Follow` → `Following`, and a signed-in Creators I Follow view. Import acceptance needs an actual list with pagination; mutation acceptance needs the free action and resulting state, separately from notification preferences. Creator webhooks remain event integrations, not a post reader.

**Afdian.** The developer guide documents `/api/open/query-order` and `/api/open/query-sponsor`, developer dashboard `user_id`/API token, JSON results and page counters. Orders are newest-first, 50/page; sponsors are relationship-time descending, 20/page. `data.list`, `total_count`, `total_page`, sponsor `current_plan/sponsor_plans`, and `user.user_id/name/avatar` belong to those resources. A sponsor nickname is nonunique, and that avatar must not become a creator avatar. Signed requests use `user_id`, JSON-string `params`, seconds `ts` and `sign`; token participates in signing. These are creator commerce methods, with no accepted post-body/media endpoint. Keep sponsor/order payloads private and collect no payment history for an ordinary reader.

**Fansly.** Model access as alternatives containing conjunctions: one option can require follow **and** payment; another can require subscription **and** payment. Preserve the effective result for locked text and each media object rather than flattening a post to one boolean. Official help also distinguishes purchased media from tip-unlocked media when permissions change. Free following may require an existing verified payment method; this research never adds one. Current subscription, time window and private-list gates must be observed without initiating a transaction. The next fixture must demonstrate readable timeline with locked media, already-owned media and a denied object; text visibility alone cannot accept the media adapter.

**FANBOX.** Blog/Image/File/Text/Video-or-Music are documented post styles. Blog posts may interleave files, text and embeds, so a flat gallery loses meaning. Attachment help lists images including GIF; audio; video files; ZIP/PDF/TXT/PSD/CLIP, with 300 MB file and 30 MB cover limits. Preserve a video's attachment role independently from an embedded player; animated GIF requires multi-frame playback verification. [Follow help](https://fanbox.pixiv.help/hc/en-us/articles/360000230381-I-want-to-follow-a-creator) documents `+ Follow` and Followed Creators; [support status help](https://fanbox.pixiv.help/hc/en-us/articles/360000232262-I-can-t-follow-a-creator-I-m-supporting) documents the transition to Supporting. Neither establishes machine-readable following export or reader schema.

**Fourthwall.** The current documented reader route is `GET https://api.fourthwall.com/open-api/v1.1/memberships/posts`, OAuth `memberships_read` or an API key, optional `X-ShopId`, required `state` (`Published`, `Scheduled`, `All`), `page`, `limit`, `search_query`, `types[]`, `ids[]` and `tags_ids[]`. The response documents typed `posts` plus `pagination.pages/limit/page/total`; text examples include `id`, `title`, `description`, `liveAt`, `path` and `access` tiers/price. Single resource uses `/posts/{id}`. Credential flow and tenant binding need a legitimate creator/shop fixture; a public storefront token must not be substituted. No request to create/delete posts, purchase content or mark a download complete belongs in discovery.

**itch.io.** Current [OAuth scopes](https://itch.io/docs/api/oauth#scopes) and the [October 12 administrator announcement](https://itch.io/t/7114687/oauth-updates-authorization-code-flow-device-login-new-scopes) add `game:view:uploads` and name `/games/:id/uploads`, `/games/:id/download-sessions`, `/uploads/:id/download`. They provide a better documented candidate than assuming buyer files require only page scraping. Do not invent HTTP verbs, payloads, response fields or transfer success where the inspected reference omits them. For `/profile/owned-keys`, request successive pages until an **empty** page; short pages may have successors. The dedicated workbench retains current versus historical release-file distinctions and multi-author samples.

**Gumroad, OnlyFans and mirror candidates.** Current Gumroad API/Library/customer-help direct fetches returned no readable lines; indexed official help remains a lead. No undocumented buyer endpoint or field is accepted. OnlyFans terms returned a non-retryable error; third-party “OnlyFans API” providers are not a first-party API contract, and archived terms do not establish current permission. Pawchive's homepage and favorites redirect are directly observed; its Swagger iframe was unreadable. Do not follow importer instructions requesting original-service session credentials. None of these failures can be replaced by search snippets, mirrored paid bodies or a generic downloader claim.

### Operation acceptance gates

For every resolved service, maintain separate receipts for **text**, **author**, **avatar**, **ordered images**, **video**, **animated GIF**, **attachments**, **following**, **login** and **entitlement**. Use explicit `unverified`, `documented`, `observed`, `executed` or `denied` states; never fill missing states from a neighboring platform. Each receipt identifies origin, account state, sample URL/ID, representation, timestamp and limitations. Source cookies, signed delivery tokens and private content are excluded from public receipts.

1. Join stable post and author identifiers, retain display-name aliases and prove the avatar belongs to the author rather than a commenter, cover, product or sponsor.
2. Compare full accessible body and ordered mixed media with the normal authorized view. Keep teaser/full distinction, external embeds, unavailable media and missing files visible. An image URL is weaker evidence than decode; a player is weaker than successful playback.
3. Verify an explicitly available authorized file with byte count/hash and archive integrity when applicable. Record native restrictions and expiry; discovery never spends credits, unlocks pay-per-view, activates a license or bypasses DRM.
4. Verify signed-in and signed-out boundaries plus free/member/tier/already-purchased/expired access separately. Login success cannot certify paid entitlement. Preserve per-object denials and rate limits.
5. Verify native-follow list completeness, free mutation and undo only within user-authorized scope; local bookmarks remain independent. Following, mailing lists, membership and ownership retain separate fields.
6. Establish actual pagination terminal signals, overlaps, edits, deletions and revoked files before claiming complete history. Require explicit platform/method permission along with account authorization.

## Shared extraction contract (proposed design)

These are original engineering recommendations. They describe what an adapter should verify, not undocumented platform capabilities that have already been observed.

Use `Author(platform, platformAuthorId?, canonicalProfileUrl, displayName, avatarUrl?, avatarEvidence, aliases[])`; `Content(platformContentId?, canonicalUrl, authorRefs[], title?, publishedAt?, updatedAt?, bodyBlocks[], accessState, completeness)`; and distinct `Media` and `Attachment` records. Store transport URLs separately from identity URLs. An image visible in a product gallery is preview media; an archive, package, model, plugin, PSD or named downloadable document is an attachment. An embedded YouTube/Vimeo player stays an external embed, not a platform-original downloadable video. Preserve text and media order rather than flattening the whole page into a gallery.

Prove avatar attribution using an author/profile relationship or the author header in verified platform chrome. Do not use the first image, site logo, post cover, product thumbnail, Open Graph image, supporter avatar or commenter's image as the author avatar. Store the avatar source URL and attribution confidence. A missing avatar is acceptable; an incorrect avatar is a data-integrity failure. Do not merge accounts solely because names or images match; prefer creator-declared cross-links.

Identity keys are platform IDs when officially returned or directly observed in an authorized fixture. Until then, canonical URL is an explicitly provisional key. Never invent undocumented property names in production parser code based on this research. Account/session partition keys must be included for restricted content snapshots, so one account's paid body never leaks into another account's preview cache.

Access states: `public`, `preview`, `authorized`, `login_required`, `membership_required`, `tier_required`, `purchase_required`, `age_gate`, `challenge`, `removed`, `temporarily_unavailable`, `unknown`. HTTP 200 containing a login/paywall/challenge page is not success. A listed attachment may exist while its download remains unavailable. Keep `contentComplete`, `historyComplete` and `downloadAuthorized` independently measurable.

Each native-pagination implementation must preserve a cursor/checkpoint, deduplicate stable IDs, detect repeated cursors/URLs, and stop on the verified terminal signal. Never assume infinite-scroll DOM contains all historical posts. Preserve pinned status without letting a pinned old post define the history watermark. Page count, oldest retrieved date and last verified checkpoint belong in sync diagnostics.

Treat signed URLs, receipt links, download keys, magic links, cookies, tokens and private RSS URLs as secrets. Show the canonical public post/item URL in provenance. Resolve downloads only when needed through the same legitimately authorized context; do not remove signature/expiry parameters from actual requests. Never forward a platform session to an arbitrary external file host. External-host resolver needs its own domain allowlist, access check, size/type validation and safe redirect policy. Do not follow instructions embedded in creator posts as app commands.

## Twelve deeper adapter recipes

The following recipes are **proposed implementation and acceptance plans**. Only the short “verified basis” statements are source-derived facts; exact private payload shapes, selectors, cursor names and native-follow actions remain unverified unless stated otherwise. All fixture collection must use the user's legitimate access or creator-provided test content and comply with the platform's supported methods.

### 1. Patreon — API v2 first, web entitlement proven separately

**Source basis.** The official v2 reference documents campaign/post/user IDs, campaign post listing, post HTML/embed fields, explicit fields/includes and the `campaigns.posts` scope. V1 retirement is documented for October 7, 2026, with individually granted extensions possible through January 20, 2027; the notice does not prove live shutdown for every account. [API reference](https://docs.patreon.com/).

**Plan.** Keep `campaignId`, `userId` and `postId` distinct. Resolve author display name/avatar only from its related user/campaign record; record which entity is being followed. Use returned pagination links rather than constructing guessed web cursors. Render sanitized HTML into ordered blocks and preserve embeds. For actual downloadable mod files, require a verified attachment relationship or explicit authorized download control; neither an embed nor campaign cover is an attachment. Before declaring patron reading, test OAuth authorization for a campaign the patron supports but does not own. If the API cannot provide the requested paid body, retain a locked/partial record and offer the site; an authorized browser path needs separate implementation evidence. Local follow is independent of membership. Native joining, upgrade and renewal are excluded.

**Acceptance fixtures.** Public text; gallery+archive; video embed; tier-locked preview; legitimately entitled full post; revoked/expired access; renamed creator; null/avatar field; pinned old post; repeated page cursor. Assert no content truncation, correct author image, unique post IDs and zero billing writes.

### 2. SubscribeStar and SubscribeStar.adult — shared mechanics, separate trust boundaries

**Source basis.** Both official API pages document read-only OAuth2 GraphQL and restrictions on benefits outside the platform. [.com API](https://www.subscribestar.com/api), [.adult API](https://subscribestar.adult/api). The adult help documents mixed post attachments and external archive links. [Help](https://subscribestar.adult/help).

**Plan.** Implement one schema-driven engine with two platform IDs and isolated origins, tokens, login states and caches. Resolve creator ID/name/avatar only from an actually available profile field or verified header. Consider permitted subscription relationships with least required scopes, not financial history by default; do not accept an off-platform full-content reader until separate platform permission is established. Enumerate accessible connections using documented edge cursors/pageInfo. Do not extrapolate payment cursor shape into post history until the post surface is observed. For web bodies, distinguish text, gallery positions, native attachment metadata and outbound links. A link is only a reference until its destination independently authorizes access. Record `nativeSubscription` as read-only state; local follow remains available. The full-content-reader recipe remains unaccepted without platform permission; an authorized user account alone does not satisfy this policy gate. Review the adult origin independently.

**Acceptance fixtures.** Same vanity on both domains; different account entitlements; free versus paid tier; gallery embedded inside text; native ZIP; external-host link; expired token; missing schema field; login/challenge response; unsupported private body. Ensure no `.com` token reaches `.adult` or an attachment host.

Parse post body order and audio/video embeds; resolve shop delivery from the user's actual purchase download view. Do not treat payment webhook data as a supporter-readable post feed. A successful guest payment followed by locked posts should produce `payment_linking_required`, with the site's normal recovery flow. Local follow and observed native follow are distinct. **Acceptance fixtures.** Public post; tier-only full body; gallery image; shop item with multiple files; physical item; unlinked guest payment; changed slug; deleted/under-review page; pagination spanning pinned item; expired delivery URL. **Source basis.** BOOTH documents shop follows and owned download delivery. Jinxxy's official help confirms a creator-store API, while the current schema page returned no readable body. Payhip's official help confirms coupon/license-key management, not a general buyer-library API. [BOOTH downloads](https://booth.pixiv.help/hc/ja/articles/231598787), [BOOTH follow](https://booth.pixiv.help/hc/ja/articles/231285648), [Jinxxy API](https://api.creators.jinxxy.com/v1/docs), [Payhip API](https://help.payhip.com/article/347-public-api).

**Plan.** Reuse normalized product/file/variant structures, while implementing three separate identity and session resolvers. A VRChat avatar listing's preview artwork is not the seller avatar. Keep seller ID/profile, product ID, purchased license tier, version and file ID distinct; retain cross-store links as evidence without auto-merging accounts. Enumerate public catalog separately from the user's owned-products/download view, each with verified pagination. Preserve rich product descriptions and galleries; list actual `.unitypackage`, archive, Blender/source, textures and documentation as attachments only when present in entitled delivery. Do not assume a publicly listed product's files are accessible. Native BOOTH follow is documented; Jinxxy/Payhip follow states remain unknown until tested. The app's local author follow is uniform across all three.

**Acceptance fixtures.** One seller cross-linking all three stores; impersonator with copied avatar; free product; already-owned paid tier; several platform/source formats; updated version; removed file; refunded Payhip access; expired delivery URL; BOOTH physical goods. Verify exact seller and purchased variant, no licenses activated, no purchases made.

### 12. Paid publications — Substack, Ghost and private Locals RSS

**Source basis.** Substack documents audience-specific body sections with an unsubscribed RSS variant. Ghost documents public API authors with `id`, `name`, `profile_image`, and posts with HTML/author includes. Locals documents per-account revocable private RSS. [Substack sections](https://support.substack.com/hc/en-us/articles/50558240901268-How-do-I-add-audience-specific-content-to-a-post-on-Substack/), [Ghost authors](https://docs.ghost.org/content-api/authors/), [Ghost posts](https://docs.ghost.org/content-api/posts/), [Locals RSS](https://support.locals.com/en/article/what-is-rss-and-how-do-i-use-it-ekrqi/).

**Plan.** Keep publication identity distinct from bylined author identity/avatar and namespace IDs by canonical origin. Use Ghost public API only for content it actually returns; a public key is not member authentication. Preserve article HTML as ordered blocks, external embeds, native audio/video media and explicitly delivered files. Feed GUIDs are opaque IDs; do not assume they equal post IDs. Track feed coverage independently of full archive coverage and follow actual archive pagination where verified. Private RSS URL is credential material; public article URL is provenance. Authorized website body snapshots are account-specific and may differ from RSS. Local following must not start email subscription or paid membership.

**Acceptance fixtures.** Guest byline; several authors; publication logo versus author avatar; free preview and paid full body; audience-specific blocks; same post fetched through RSS and web; Locals secret rotation; access loss; custom domain; missing feed history. Assert public cached body never overwrites a more complete authorized snapshot and private data never enters a public cache.

## Japanese ecosystem addendum: Ci-en and DLsite

Ci-en and DLsite are separate adapters even where creator discovery or account infrastructure is related. Ci-en free follow, support month, active tier, backnumber ownership and creator-set viewing window need separate fields.
